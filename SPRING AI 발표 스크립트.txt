1. 오프닝 (강의 개요)

오늘 강의에서는 단순히 단어를 찾아내는 금칙어 필터링을 넘어, 문장의 문맥과 의도를 파악하는 지능형 필터링 시스템을 구현해 보겠습니다.

이를 위해 세 가지 핵심 기술이 유기적으로 작동하게 되는데요.
언어의 의미를 수치화하여 벡터 공간에 배치하는 임베딩,
방대한 데이터 속에서 관련 정보를 실시간으로 찾아내주는 RAG,
그리고 최종적으로 문맥을 읽고 인간처럼 판단하는 LLM의 개념을 다시 한번 정리하며, 이 기술들이 하나의 파이프라인으로 연결되는 과정을 살펴보겠습니다.


전체구조를 먼저 보시면 어드민과 유저가 있습니다.
초록색으로 되어있는 부분은 spring boot server를 의미하고,
보라색은 임베딩모델을, 파란색은 llm모델을 의미합니다.

저희는 내부망 환경에서도 안전하게 사용할 수 있도록 Ollama를 사용했고,
임베딩 모델은 BGE-M3, LLM은 Gemma2:9B, 벡터 데이터베이스는 PostgreSQL의 PGVector를 사용했습니다.

먼저 임베딩 부터 살펴보겠습니다.
지난시간 강의자료를 보시면
(모듈7장 맨위)
임베딩은 사람의 언어를 AI가 이해할 수 있는 숫자 벡터로 변환하는 기술입니다.
숫자벡터는 여러개의 부동 소수점으로 이루어진 숫자배열을 의미합니다.
하지만, 임베딩에서 중요한것은 이러한 숫자자체가 아니라 벡터 간의 거리 관계입니다.
ai는 이 데이터의 의미를 벡터공간에서의 거리관계로 표현하기 때문입니다.
즉, 의미가 비슷한 데이터는 벡터 공간에서 서로 가까운 위치에 놓이고, 의미가 다른 데이터는 멀리 떨어진 위치에 배치되는 것입니다.

벡터에는 차원이라는 개념이 존재합니다.
차원은 쉽게 말해서 AI가 데이터를 이해하기 위해 참고하는 정보의 개수라고 보시면 됩니다.

아래보시는것과 같이 3차원인 경우는 "사과" 라는 단어에 대해서 3개의 데이터만을 가지고 있지만,
1536차원인 경우는 한 단어에 대한 연관데이터가 1536개가 있다는것을 의미합니다.
즉, 차원이 높을수록 데이터는 공간 상에서 더 정교하고 고유한 위치를 갖게되는것입니다.

하지만 차원이 높다고 무조건 좋은건 아닙니다.
차원이 높아질수록 더 정교한 표현이 가능하지만, 그만큼 속도가 느려지고, 너무 많은 정보로 인해 할루시네이션이 발생할수있다는 단점이 있습니다.

비속어 필터링 기능처럼 속도와 정확도가 중요한 시스템에서는 높은 차원일수록 오히려 비효율적이 될 수 있습니다.
그래서 저희는 속도와 문맥 이해 성능의 균형이 좋은 1024차원의 BGE-M3 모델을 선택했습니다.

BGE-M3는 100개 이상의 언어를 지원하면서도, 특히 한국어 성능이 뛰어난 모델입니다.
비속어 필터링에서는 단순 단어 매칭보다 문맥과 뉘앙스를 이해하는 것이 중요하기 때문에, 한국어 문맥 이해 성능이 좋은 BGE-M3를 선택했습니다.


다음 llm모델입니다.
구글에서 제공한 gemma2:9b 모델입니다.
여기서 9b는 90억개의 파라미터를 가지고 있다는 것을 의미합니다.

LLM에게 파라미터는 인간의 시냅스와 비슷한 역할을 하는 수치로,
파라미터가 많을수록 ai는 더 복잡한 문맥을 파악하고 방대한 지식을 기억해 정교하게 응답할 수 있습니다.

(강의자료)
이전 강의자료를 보시면 LLM의 구조적 특징에는 파라미터라는게 있습니다.
-파라미터설명-

하지만 이전에 임베딩 모델과 마찬가지로 ,파라미터가 많아질수록 일반적으로 모델은 무거워진다는 단점이 있습니다.
Llama 3(8B)와 Gemma 2(9B)를 비교해보았습니다.
Llama 3는 80억개의 파라미터를 가지고 있고, Gemma2는 90억개의 파라미터를 가지고 있습니다.
이 두 모델은 약 10억 개의 파라미터 차이가 있음에도 실제 응답 속도에는 큰 차이가 없었습니다.

이게 바로 제가 gemma2를 선택한 이유이기도 합니다.
Gemma 2는 일반적인 어텐션과 슬라이딩 윈도우 어텐션을 1:1로 섞어서 사용하기 때문입니다.
모든 단어를 한꺼번에 계산하는 대신, 슬라이딩 윈도우가 가까운 단어들을 효율적으로 처리하여 메모리 사용량을 획기적으로 줄여줍니다.
이렇게 아낀 메모리와 계산 자원을 멀리 떨어진 문맥을 파악하는 일반 어텐션에 분배함으로써,
90억 개의 파라미터를 가졌음에도 80억 개 급의 모델만큼 가볍고 빠른 속도를 유지할 수 있는 것입니다.
결국 입력 문장이 길어져도 앞부분의 맥락을 놓치지 않고 끝까지 파악할 수 있는, Gemma 2(9B)를 선정하게 되었습니다.

반면, Llama 3는 프롬프트 지시사항을 매우 정확하게 이해하고 수행하는 '통제력'을 강점으로 가지고 있습니다.
만약 Gemma 2처럼 정교한 맥락 파악보다는 빠른 응답 속도와 프롬프트를 통한 세밀한 컨트롤이 더 중요하다면 Llama 3가 좋은 대안이 될 수 있습니다.

마지막 Vector DB입니다.
저희는 벡터 데이터베이스로 PostgreSQL의 pgvector를 채택했습니다.

가장 큰 이유는 Spring AI와 같은 최신 프레임워크와의 완벽한 호환성입니다.
pgvector는 공식적인 벡터 DB로서 모든 기능을 지원하며, 특히 PostgreSQL의 JSONB 타입을 활용해 메타데이터나 비정형 데이터까지 유연하게 관리할 수 있다는 강점이 있습니다.

검색 알고리즘으로는 HNSW(Hierarchical Navigable Small World) 방식을 선택했습니다.
HNSW는 데이터가 추가될 때마다 인덱스를 실시간으로 업데이트하면서도, 수백만 건의 데이터 속에서 밀리초 단위의 압도적인 검색 속도와 높은 정확도를 보장합니다.
물론 메모리 효율이 더 좋은 IVF 방식도 있습니다.
하지만 IVF는 데이터가 증가할수록 정확도가 떨어지고, 성능 유지를 위해 주기적으로 인덱스를 재빌드(Rebuild)해야 하는 운영상의 부담이 크다는 단점이 있기 때문에
메모리 점유율은 조금 높더라도 별도의 재빌드 없이 최상의 속도와 정확도를 유지해주는 HNSW 인덱스를 사용했습니다.

다른 데이터베이스들과도 비교해 보았습니다.
MySQL이나 MariaDB는 최근 벡터 기능을 도입 중이지만, pgvector만큼 다양한 인덱싱 알고리즘이나 Java 라이브러리와의 연동성이 아직 부족합니다.
Oracle은 강력한 벡터 기능을 제공하지만 높은 라이선스 비용이 부담되며, 티베로 등 국산 DB는 아직 해당 기능을 지원하지 않는 것으로 확인되었습니다.

결론적으로, 기술적 성숙도와 성능, 그리고 방대한 커뮤니티 지원 규모를 종합적으로 고려했을 때, 현시점 가장 적합한 것은 PostgreSQL의 pgvector였습니다

이제 앞서 설명드린 모델들을 활용해 실제 비속어 필터링 시스템을 어떻게 구축했는지 전체 구성을 보시겠습니다.

1. 데이터 적재 (Ingestion Flow)
먼저, 학습되지 않은 신규 비속어를 Admin이 직접 등록하는 과정입니다. 장표에는 인증 단계가 포함되어 있지만,
이번 실습에서는 핵심 로직인 '입력된 문장을 임베딩 모델을 통해 벡터화하고, 이를 RAG에서 활용할 수 있도록 pgvector DB에 저장'하는 과정에 집중하여 구현했습니다.

2. 실시간 필터링 (Filtering Flow)
다음은 실제 유저의 메시지가 처리되는 과정입니다. 유저가 문장을 입력하면 ChatClient와 AroundAdvisor를 거쳐
1단계는 전처리, 2단계는 RAG 기반 유사도 검색, 3단계는 LLM 기반 최종 문맥 검증으로 총 3단계의 심층검증이 진행됩니다.

하단의 데이터 흐름도(Sequence Diagram)를 통해 더 자세히 살펴보겠습니다.

어드민이 메시지를 입력 하면 해당 문장을 벡터화하고 반환 받은 값을 vector db에 저장하고, 적재완료 알림을 받게됩니다.

[1단계: 전처리 및 로컬 필터링]
유저가 메시지를 입력하면 먼저 4단계의 전처리(Normalizing, Regex 등)를 거칩니다. 여기서 명백한 비속어가 감지되면 즉시 차단됩니다.

[2단계: RAG 기반 유사도 검색]
로컬 필터링을 통과했다면, Spring AI를 활용해 입력 텍스트를 벡터화한 뒤 pgvector에서 2차 유사도 검색을 수행합니다.
기존에 등록된 비속어 데이터와 유사도가 높을 경우, 여기서 다시 한번 즉시 차단 처리가 됩니다.

[3단계: LLM 심층 검증 및 피드백]
위의 모든 과정을 통과했더라도 문맥상 검증이 필요한 경우, 마지막으로 LLM(Ollama)을 통한 최종 판단을 진행합니다.
이 단계까지 도달한 데이터는 별도의 테이블에 기록하여 관리자가 추후 검토할 수 있게 했습니다.
만약 LLM이 이를 새로운 비속어로 판단하면, 자동으로 어드민 API를 호출해 벡터 DB에 재학습시키는 구조로 설계되었습니다.

결론적으로, 이번 실습에서는 다음 4가지 핵심 시나리오를 직접 확인해 볼 예정입니다.
1. 어드민의 신규 비속어 등록 과정으로 임베딩 후 벡터 DB 적재 과정을 확인하고
2. 기존 데이터와의 유사성을 통한 필터링으로 RAG를 통한 유사도 비교하는 과정을 확인할예정입니다.
3. RAG를 통과한 문장의 문맥 판단을 위한 LLM 최종 검증을 통해 chatClient, 프롬프트 엔지니어링, 구조화된 출력, advisor 활용까지 확인해보도록 하겠습니다.
4. 전체 통합 로직: 전처리부터 LLM 검증까지 이어지는 전체 파이프라인
그럼 지금부터 실습을 통해 하나씩 확인해 보겠습니다.

2. 시스템의 심장: 데이터 적재와 Spring AI (Vector Store & RDB)

실습을 시작하기 전에 올라마 설치를 먼저 진행해보도록 하겠습니다.

올라마 설치는 공식홈페이지에서 설치파일을 다운받아도 되고, 명령어를 사용해서 cmd 를 통해 다운받아도 됩니다.
설치를 하게되면 보시는것처럼 애플리케이션이 나타나고, 들어가서 보시면, 사용가능한 모델을 확인하실수있습니다.
직접 명령어를 통해 설치도 가능하지만 사용할 모델을 선택한후에 질문을 하게되면 자동으로 설치되니 사용할 모델을 선택해서 테스트 해보실수있습니다.


이제 설정방법을 보시겠습니다.

그리고 마찬가지로 CaseB에 있는 올라마 설정을 그대로 입력해주시면 되고,

build.gradle 파일과 application.properties 파일 설정을 보겠습니다.
임베딩 모델은 BGE-M3 이고, LLM모델은 gemma2:9b를 선택했기때문에 보시는것과같이 설정을 해주시면 됩니다.

마찬가지로 PGvector를 프로젝트에 적용하기 위해서는 라이브러리 의존성과 데이터베이스 설정이 필요합니다.
db 설정도 보시는 것과 같이 application properties 파일에서 하시면 되고,
아래 설정같은 경우에는 자동생성기능을 사용할때 해주셔야하고, db를 따로 생성하고 진행하는 경우에는 설정하지 않으셔도 됩니다.
(쿼리보여주기)

pgvector를 사용하려면 아래 명령어를 통해 Extension을 활성화해야합니다.
아래 명령어를 실행을 해 주셔야만 vector 라는 새로운 데이터 타입과 관련연산자들을 사용하실수있습니다.
CREATE EXTENSION IF NOT EXISTS vector;

pgvector를 사용하실때 주의하실점은
postsql 버전 최소 13이상을 사용해주셔야하고 , HNSW 인덱스를 사용하려면 최소 14이상을 권장하고있습니다.
그래서 안전하게 사용하려면 15~16버전을 사용하시는 것을 가장 권장하고 있습니다.
--버전확인
SELECT version();
버전 확인을 하시려면 이 쿼리를 확인해보시면 되는데 보시는것과 같이 저는 16.13버전을 사용했습니다.


이제는 저희가 실습에서 사용할 테이블과 미리 학습한 데이터를 설명 드리도록 하겠습니다.
bad_word, pending_bad_word, vector_store, new_vector_store(자동기능) 총 4개의 테이블을 주로 사용할예정입니다.

- bad_word (RDB): 이 테이블은 문장이 아닌 확정된 비속어 리스트를 관리하는 테이블이고,
- pending_bad_word (검토 대기 데이터): 모든 전처리 과정과, RAG 를 통과한 후에 LLM으로 가는 모든 데이터를 적재하는 테이블입니다.
(각 테이블 컬럼 설명)

다음 vector_store 테이블입니다.

 spring ai 에서 제공하는 기본 테이블명은 vector_store이기 때문에 동일하게 테이블을 생성하였고,
만약에 테이블명을 변경하는 경우에는 따로 application.properties 파일에 지정을 해주셔야합니다.
그리고 new_vector_store는 뒤에서 한번더 설명드릴건데, db 자동생성기능을 보여드리기 위해 테스트할 테이블입니다.

이때 검색의 기준이 되는 것이 바로 '코사인 유사도'입니다.
코사인 유사도 방식은 두 문장이 얼마나 비슷한 의미인지를 방향으로 측정한 것으로
 vector db는 기본적으로 "유사도"가 아닌 "거리"를 계산합니다.
 그렇기 때문에 거리가 같다면 즉, 의미가 동일하다면 0이 되게 되는것입니다.

 하지만 우리는 보통 '유사도 1.0(100%)'이 가장 닮았다고 직관적으로 이해합니다.
 이게 바로 spring ai 가 알아서 변환을 해주고 있기 때문입니다.
 Spring AI의 PgVectorStore는 DB에서 가져온 거리 값을 '1 - 거리' 공식으로 계산하여, 우리가 이해하기 쉬운 유사도 점수(Similarity Score)로 자동 변환해 줍니다.

물론 벡터 유사도에는 코사인 유사도만 있는 것은 아닙니다.
두 점 사이의 최단 직선거리를 측정하는 유클리드거리와 두 벡터의 성분을 곱하여 합산하는 내적이라는 다른 방식들도 존재합니다.

그럼 저희는 왜 코사인유사도 방식을 선택한걸까요 ?

그건 바로 자연어 처리 때문인데요. 자연어데이터는 문장의 길이가 제각각입니다.
유클리드거리와 내적방식같은 경우는  의미를 파악하는게 아닌 문장의 길이를 기준으로 데이터의 유사도를 판단합니다
문장이 길어지고 단어가 많아지게 되면 벡터의 길이가 길어지게 되고, 단순히 '길이가 다르다'는 이유로 "다르다"는 잘못된 판단을 할수있습니다.
반면에 코사인 유사도는 벡터의 길이는 무시하고, 어떤 방향을 향하고있는지만을 보기 때문에 길이에 상관 없이 "의도와 문맥"을 보고 데이터를 판단합니다.

그래서 저희는 문장의 길이에 상관없이 사용자의 의도와 문맥을 정확히 파악하기 위해서 코사인 유사도를 선택하였습니다.
만약에 정확한 수치데이터를 비교하거나 이미지를 처리하는 경우 등에는 유클리드거리 방식을 사용하고
선호도를 계산하거나 추천알고리즘 또는 초고속 검색엔진등에는 내적방식이 사용된다고 이해하시면 됩니다.


(강의자료)
- Vector Store (임베딩 저장소):
Spring AI에서 제공하는 Vector Store는 기본적으로 다음과 같은 4개의 컬럼을 가지고 있습니다.

id: 데이터 식별자
content: 임베딩 대상이 되는 텍스트
metadata: 부가 정보 저장용 메타데이터
embedding: 텍스트를 임베딩한 벡터 값

추가 컬럼을 생성하는 것도 가능하지만,
그럴 경우 Vector Store에서 제공하는 기본 기능을 사용하는 데 제약이 생길 수 있습니다.
따라서 별도의 정보가 필요할 경우에는 컬럼을 추가하기보다는 metadata 안에 키를 추가하는 방식을 권장하고 있습니다.

RAG 시스템을 구축하기 위해 가장 먼저 선행되어야 할 것은 데이터 준비입니다.
 지난 시간에 설명드렸던 ETL(Extract, Transform, Load) 파이프라인이 바로 이 과정인데요.
다양한 소스에서 데이터를 추출(Extract)하고, 이를 AI가 이해할 수 있게 정제 및 임베딩(Transform)하여,
최종적으로 벡터 저장소에 적재(Load)하는 일련의 과정을 의미합니다.

저희가 학습에 사용한 데이터는 AI Hub에서 다운로드한 자료이며, 기존 학습 데이터는 JSON 파일 형태로 확인하실 수 있습니다.
데이터 구조를 보면, sentence라는 키 안에 하나의 대화가 문장 단위로 분리되어 저장되어 있습니다.

저희는 이 문장을 기준으로 각각 임베딩을 생성하여 Vector Store에 데이터를 저장했습니다.
또한, is_immoral 값이 true / false 인 경우를 비교해서 확인할 수 있으며,
이를 통해 비속어 여부에 따라 데이터가 어떻게 분류되는지도 확인하실 수 있습니다.
(is_immoral이 true인경우 false인경우 비교해서 보여주기)

Metadata 저장 방식
학습된 데이터를 실제로 활용하기 위해, 문장에 해당하는 전체 object를 metadata 안에 JSONB 형태로 저장해두었습니다.
이렇게 하면, 임베딩 검색 결과에 대해 문장뿐 아니라 관련된 모든 원본 정보를 함께 활용할 수 있습니다.

마지막으로 주의하실 점이 하나 있습니다.
비속어가 아닌 경우 데이터에 "votes": null과 같은 값이 존재하는데, JSONB 타입은 특정 키의 값이 null인 경우 저장이 불가능합니다.
따라서 데이터를 저장할 때는, null 값을 제거하거나 기본값으로 변환하는 등 저장 시점에서 반드시 처리해 주셔야 합니다.

6. API v4: 전처리(Preprocessing) - "꼼수 차단하기"
마지막 /v4는 실전 대응을 위한 전처리 단계입니다.

spring ai 가 제공해주는 safeGuardAdvisor를 사용하게 되면 질문에 대한 검열작업이 자동으로 수행되지만,
정확하게 어느 단어에서 비속어로 차단이 되었는지, 유사도가 어느정도 였는지 알수없고 정확한 수치제어가 힘들다는 단점을 가지고 있습니다.
또한 명백한 욕설조차 문맥 분석을 위해 LLM을 호출하므로, 불필요한 비용과 응답 지연(Latency)이 발생합니다

이러한 단점을 보완하기 위해, 저희는 LLM에 도달하기 전 3단계의 전처리 과정을 구현했습니다.

사용자들은 "바.보", "바   보", "B@bo"처럼 공백이나 특수문자를 섞어 필터를 피하려 합니다.
/v4에서는 BadWordPendingService를 통해 다음과 같은 3단계 정밀 전처리를 수행하여 이런 노이즈를 제거합니다.

1) 텍스트 정규화 및 클리닝 (Clean & Normalize)
사용자가 공백이나 특수문자로 필터를 피하려는 시도를 무력화합니다.
- NFC 정규화: 한글 자음/모음이 분리된 경우를 대비해 표준 완성형 한글로 통일합니다.
- 노이즈 제거: 정규식을 이용해 특수문자, 공백, 이모지를 모두 제거하고 한글, 영문, 숫자만 남깁니다.
- 반복 문자 축소: "바보보보보"와 같이 필터링을 피하기 위해 반복된 글자를 "바보"로 축소하여 검사 효율을 높입니다.

2) 정규식(Regex) 기반 고속 필터링
- 특수문자나 숫자가 중간에 섞인 변칙적인 비속어 패턴(예: 시1발, ㅂㅅ 등)을 미리 컴파일된 거대 정규식으로 1차 차단합니다.
- 이는 LLM호출 없이 가장 빠르고 효율적으로 명백한 비속어를 걸러내는 역할을 합니다.

3) 자모 분리 및 Fuzzy Matching (유사도 검사)
- "Jaro-Winkler 유사도": 분리된 자모를 바탕으로 DB에 등록된 비속어와 시각적/청각적 유사도를 계산합니다. (임계치 0.88 이상 차단)

- "자모 분리(Decomposition)": 한글을 'ㅂ, ㅏ, ㅂ, ㅗ'와 같이 초성, 중성, 종성으로 분해합니다.
- "슬라이딩 윈도우": 문장 속에 숨겨진 비속어를 찾기 위해 창문을 밀듯 한 글자씩 옆으로 이동하며 부분 일치 여부를 정밀하게 검사합니다.

7. 클로징 (정리)
정리하겠습니다. 우리 프로젝트는 데이터를 비동기로 스마트하게 적재하고(Initializer), 의미를 숫자로 바꾸어(Embedding),
지식 저장소에서 검색하고(RAG), AI의 뇌를 빌려 정확히 판단(LLM & Prompt)한 뒤,
사용자의 꼼수까지 걸러내는(Preprocessing) 완벽한 AI 필터링 파이프라인을 구축한 것입니다.
