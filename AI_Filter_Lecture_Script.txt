1. 오프닝 (강의 개요)
이번시간에 저희는 'AI 기반 비속어 필터링 시스템' 을 구현 해보도록 하겠습니다.

먼저 프로세스를 확인해보시면
초록색으로 되어있는 부분은 spring boot server를 의미하고,
보라색은 임베딩모델을, 파란색은 llm모델을 의미합니다.

이전에 강의했던 자료를 보시면, 올라마의 특징은 이렇게 있습니다.

저희는 보안을 위한 내부용 올라마를 선택을 했고,
임베딩모델은 bge-m3 를, llm모델은 gemma2:9b를 사용했고, vectorDB는 postgresql 의 PgVector를 사용하였습니다.


BGE-M3 모델은, 100개 이상의 언어를 지원하면서도 한국어에 특화되어있고, 비속어의 미묘한 뉘앙스부터 정확한 금칙어 매칭까지 파악할수있다는 장점을 가지고 있습니다.
그리고 BGE-M3는 1024차원을 가지고 있습니다.
차원이 높을수록 정보를 세밀하게 담을 수 있어서 좋다고 생각할수있지만, 차원이 높을수록 느려진다는 단점도 있고,
비속어 필터링처럼 속도와 정확도가 중요한 시스템에서는 차원이 너무 높아지면 응답 속도가 느려지고, 오히려 할루시네이션이 발생할수있기 때문에
연산속도는 빠르고 비속어 특유의 맥락을 더 정확하게 파악할수있는 BGE-M3 모델이 가장 적합하다고 생각하여 선정하게 되었습니다.

다음 llm모델입니다.
gemma2:9b 모델을 선택했고, 9b는 90억개의 파라미터를 가지고 있다는 것을 의미합니다.
llm 모델도 마찬가지로 파라미터가 많을수록 지능이 높아지지만, 모델이 무거워져서 응답이 느려진다는 단점이 있습니다.
llama3와 gemma2:9b 두 모델을 비교해봤을때 약 10억개의 파라미터의 차이가 있지만, 실제로 응답속도에는 큰 차이는 없었고,
gemma2 모델이 한국어 문장을 조금 더 잘 이해하고, 슬라이딩 윈도우 어텐션 기술이 적용되어있어 입력 문장이 길어지는 경우에도 앞부분의 맥락을 놓치지 않고 추적이 가능하다는 장점을 가지고 있어서 gemma2:9b를 선정하였습니다.

올라마 설치는 공식홈페이지에서 설치파일을 다운받아도 되고, 명령어를 사용해서 cmd 를 통해 다운받아도 됩니다.
설치를 하게되면 보시는것처럼 애플리케이션이 나타나고, 들어가서 보시면, 사용가능한 모델을 확인하실수있고,
직접 명령어를 통해 설치도 가능하지만 사용할 모델을 선택한후에 질문을 하게되면 자동으로 설치되니
사용할 모델을 선택해서 테스트 해보실수있습니다.

마지막 Vector DB입니다.
PostgreSQL의 pgvector를 사용하였는데요

Spring AI 프레임워크 등에서도
PGvector를 공식적인 벡터 데이터베이스로 모든 기능을 완벽하게 지원하고 있다는 장점이있고,
postgresql 에서는 JSONB 타입을 기본적으로 지원하기 때문에, 메타데이터나 비정형 데이터까지 유연하게 인덱싱하고 관리할 수 있습니다.

또 pgvector는 HNSW 인덱스 등을 지원하여 수백만 건의 데이터도 밀리초 단위로 아주 빠르게 검색할 수 있습니다.
HNSW(Hierarchical Navigable Small World) 인덱스란,
데이터가 추가될 때마다 인덱스를 실시간으로 업데이트하면서도 매우 빠른 검색 속도를 유지하는 알고리즘으로 속도가 압도적으로 빠르고 정확도(Recall)가 높다는 장점이 있지만 그만큼 메모리가 많이 필요하다는 단점도 있습니다.
IVF 라는 알고리즘도 있지만, HNSW에 비해 메모리를 적게 필요하지만,  데이터가 많이 추가되면 구역 경계가 모호해져서 정확도가 떨어지고, 주기적으로 인덱스를 다시 빌드(Rebuild)해줘야 성능이 유지된다는 단점이 있어서 HNSW를 주로 사용합니다.

저희가 HNSW(Hierarchical Navigable Small World)를 선택한 이유는 대규모 데이터에서도 실시간 인덱싱과 높은 검색 정확도(Recall)를 동시에 보장하기 때문입니다.

물론 IVF(Inverted File) 방식이 메모리 효율은 더 좋지만, 데이터가 지속적으로 추가되는 환경에서는 클러스터(구역) 경계가 모호해져 검색 품질이 저하되고, 주기적으로 인덱스를 재빌드(Rebuild)해야 하는 운영상의 부담이 크다는 단점이 있습니다. 반면 HNSW는 상대적으로 메모리 점유율은 높지만, 별도의 재빌드 없이도 압도적인 속도와 정확도를 유지할 수 있어 현재 저희 프로젝트에 가장 적합한 알고리즘입니다.


MySQL / MariaDB 같은 경우는 최근들어 vectordb를 지원하고 있지만, pgvector처럼 다양한 인덱싱 알고리즘(IVFFlat, HNSW 등)이나 Java(Spring AI, LangChain4j) 라이브러리와의 완벽한 연동성은 아직 부족하다고 알려져있습니다.

 Oracle의 경우에도 최신 23c 버전부터 AI Vector Search 기능을 도입하여 프레임워크와의 연동이 가능하지만, 라이센스 비용과 초기구축 비용이 비싸다는 단점이 있습니다.
마지막으로 티베로같은 경우는 아직 지원하지 않는것으로 알려져있습니다.

이렇게 다른 vector db를 사용해도 되지만,아직은 PostgreSQL의 pgvector가 보여주는 기술적 성숙도나 성능, 커뮤니티의 지원 규모를 따라오지 못하고 있기때문에, 저희는 PostgreSQL의 pgvector를 선택하게 되었습니다.



pgvector를 사용하려면 아래 명령어를 통해 Extension을 활성화해야합니다.
아래 명령어를 실행을 해 주셔야만 vector 라는 새로운 데이터 타입과 관련연산자들을 사용하실수있습니다.
CREATE EXTENSION IF NOT EXISTS vector;

pgvector를 사용하실때 주의하실점은
postsql 버전 최소 13이상을 사용해주셔야하지만 , HNSW 인덱스를 사용하려면 최소 14이상을 권장하고있습니다.
그래서 안전하게 사용하려면 15~16버전을 사용하시는 것을 가장 권장하고 있습니다.
--버전확인
SELECT version();
버전 확인을 하시려면 이 쿼리를 확인해보시면 되는데 보시는것과 같이 저는 16.13버전을 사용했습니다.


이제 이 모델들을 사용하여 비속어 필터링 기능을 구현한 시스템 구성을 보시겠습니다.

먼저 학습되지 않은 비속어 문장을 어드민이 직접 추가할수 있도록 하는 api입니다.
이 장표에는 어드민이 문장을 입력하게 되면 인증단계를 거쳐서 지나도록 되어있는데,
이번 실습에서는 인증단계는 구현되어있지 않고,  어드민이 문장을 입력하면 임베딩 모델을 통해 임베딩을 하고, 이후에 RAG에서 사용할수있도록, vectorDB에 저장하는 로직으로 구현을 했습니다.

다음은 유저입니다.
유저가 문장을 입력하게 되면, chatClient와 AroundAdvisor를 거치고
전처리작업 L1, RAG check L2, LLM검증 L3으로 총 3단계를 거쳐 진행이 될거고, llm에서 비속어라고 판단되면 vectordb에 저장되도록 구현을 하였습니다 .

아래 데이터 흐름도를 보면서 자세하게 설명드리겠습니다.

먼저 어드민이 신규 비속어 및 패턴을 등록하기 위해 문장을 입력하게되면, 2번에서 local regex/list 동기화를 먼저 하도록 되어있는데 이 부분은 현재 구현이 되어있지 않고, 바로 3번으로 이동해서 벡터화요청을 하고 반환받은 벡터 데이터를 pgvector에 저장을 하고 적재완료알림을 받는것으로 구현해보았습니다.

다음은 유저가 메시지를 입력하는 경우입니다.
유저가 메시지를 입력하게되면 4단계의 전처리 및 로컬 필터링을 진행합니다.
전처리에서 비속어가 감지가 되었다면 즉시차단하도록 하였고,

전처리 및 로컬 필터링을 통과를 했다면, spring ai기능을 활용하여 비속어 필터링을 구현하도록 진행할예정입니다.
전처리를 통과하면 14번 텍스트 벡터화를 진행을 하게되고, 반환받은 벡터데이터로 2차 유사도 검색인 RAG를 진행합니다.
유사도가 높은 문장이 검색이 되었다면 13번과 마찬가지로 즉시차단하도록 되어있고,

위에 모든 과정을 통과했다면, LLM을 통한 검증을 한번 더 진행하도록 구현하였습니다.

RAG를 통과했더라도, 사용자의 검증이 필요한 문장들이 있을 수있기때문에 LLM 검증까지 진행이 되었다면 별도의 테이블에 해당 데이터를 저장하도록 했고,
LLM이 비속어라고 판단을 하게되면 20번에서 admin이 사용하는 api를 호출하여 임베딩한 후에 vectordb에 저장하도록 구현한것까지 확인해보도록 하겠습니다.

지금까지 설명한 흐름을 토대로 실습을 통해 확인해볼 api는 총 4가지로,
1. 어드민이 신규 비속어를 임베딩 후에 등록하는 경우
2. 사용자가 입력한 문장을 RAG를 통해 유사도 비교까지 진행하는 경우
3. 유사도비교를 통과하여, LLM 검증을 진행하는 경우
4. 전처리과정을 포함하여 1,2,3번의 로직을 모두 진행하는 경우로, 설명한 모든 로직을 확인해보도록 하겠습니다.

2. 시스템의 심장: 데이터 적재와 Spring AI (Vector Store & RDB)


먼저 이전 강의자료를 한번 더 확인해보시면,

 build.gradle 파일과 application.properties 파일 설정을 보겠습니다 .

임베딩 모델은 BGE-M3 이고, LLM모델은 gemma2:9b를 선택했기때문에 보시는것과같이 설정을 해주시면 되고
사용할 모델은 미리 pull을 실행해주셔야 문제없이 사용가능하니 주의해주셔야합니다.

db 설정도 보시는 것과 같이 application properties 파일에서 하실수있지만,
이렇게 설정을 하는것은 자동생성기능을 사용할때이고, 저는 db를 직접 생성하고 진행하였기때문에 따로 기재하지는 않았습니다.
(쿼리보여주기)

이제는 저희가 실습에서 사용할 테이블과 미리 학습한 데이터를 설명 드리도록 하겠습니다.
총 3개의 테이블을 사용할거고

- bad_word (RDB): 이 테이블은 문장이 아닌 확정된 비속어 리스트를 관리하는 테이블이고,
- pending_bad_word (검토 대기 데이터): 모든 전처리 과정과, RAG 를 통과한 후에 LLM으로 가는 모든 데이터를 적재하는 테이블입니다.

마지막으로 vector_store 테이블입니다.
vectorStore에서 제공하는 기본 테이블명은 vector_store이기 때문에 동일하게 테이블을 생성하였고,
만약에 테이블명을 변경하는 경우에는 따로 application.properties 파일에 지정을 해주셔야합니다.

RAG를 사용하기위해선 데이터가 필요합니다.
그 데이터를 준비하는 과정을 ETF 파이프라인이라고 설명드렸었습니다.
여러 데이터 소스에서 데이터를 출하고, 데이터를 정제해서 임베딩을 진행하고 vector store에 적재하는 과정을 의미합니다.

- Vector Store (임베딩 저장소):
(강의자료 오픈)Spring ai 에서 지원하는 vectorStore는 기본적으로 id, content, metadata, embedding 이렇게 4개의 컬럼을 가지고있습니다.
만약에 추가로 다른 컬럼을 생성하고 싶으시면 추가해도 되지만 vectorStore에서 제공해주는 기능을 사용하는데 제한이 생기기 때문에
필요한 컬럼이 생기면 metadata 안에 키를 추가하는것을 권장하고 있습니다.


저희가 학습시킨 데이터는 aiHub 라는 곳에서 다운받은 자료이고, 기존에 학습된 데이터를 json파일로 확인하실 수 있습니다.
데이터를 보시면, sentence라는 키 안에 한 대화가 문장단위로 나누어져 있고,
저희는 그 학습된 문장 단위로 임베딩하여 데이터를 저장해두었습니다.
(is_immoral이 true인경우 false인경우 비교해서 보여주기)
그리고 학습된 데이터를 사용하기 위해 문장에 해당하는 전체 object를 metadata라는 키 안에 jsonB 형태로 저장해 두었습니다.

여기서 주의하실점은 비속어가 아닌 경우 "votes": null,이라는 데이터가 있는데 jsonB형태를 사용하실때는 해당하는 키에 대한 값이 null이면 저장할수없기때문에 저장 시에 주의해주셔야합니다. 저는 null인 경우에는 키 자체를 제외하고 저장하도록 구현을 해 두었습니다.
(DB 보여주기)

3. API v1: 임베딩(Embedding) - "문장을 숫자로 바꾸는 마법"
첫 번째 단계인 /v1은 임베딩하는 것을 살펴보도록 하겠습니다.
(강의자료오픈)
사용자가 문장을 입력하면, 우리는 EmbeddingModel을 사용해 그 문장을 수백 개의 차원을 가진 벡터(Vector)로 변환하게 되고,
그리고 이 변환된 벡터 데이터를 Vector Store에 저장하는것입니다. 이과정은 단순히 글자를 저장하는 것이 아니라,
나중에 '비슷한 것'을 찾기 위해 공간에 '의미의 좌표'를 찍는 작업입니다.

먼저 중복데이터를 적재하지 않기 위해 문장에 대한 특정 uuid를 생성해줍니다.
그리고 spring ai 데이터 기본 단위인 document 형태로 데이터를 변환해줍니다.
document는  id,  text, media, metadata, score 를 기본으로 가지고있습니다.(라이브러리 들어가서 보여주기)

앞서 EmbeddingModel을 사용해서 벡터로 변환이 아닌 vectorStore.add 메소드만 사용한것을 보실수있습니다.

add 메소드를 들어가 보시면 doAdd 메소드를 호출하는것을 확인 하실 수 있습니다.
한번더 PGvectorStore를 클릭해서 들어가 보시면,
this.embeddingModel.embed 로 입력한 문장을 임베딩해주고, insertOrUpdateBatch를 통해 insert를 해주고 있는것을 보실 수 있습니다.

제가 중복 데이터를 적재하지 않기 위해 특정 uuid를 생성한다고 말씀드렸습니다.
여기서 보시면 on conflict 를 사용해서 id가 동일하다면 update를 하도록 되어있는것까지 확인하실수있습니다.

4. API v2: RAG(Retrieval-Augmented Generation) - "기억에서 찾아내기"
/v2에서는 드디어 AI가 '공부한 내용'을 써먹기 시작합니다. 바로 RAG 방식입니다.

입력된 문장이 들어오면, Vector Store에서 가장 유사한 비속어들을 유사도 검색(Similarity Search)으로 순식간에 찾아냅니다.
외부 LLM을 호출하기 전에 내부 저장소에서 먼저 답을 찾는 방식이라 매우 경제적이고 속도가 빠릅니다.

vector db를 조회하려면 vectorstore.similaritySearch 메소드를 사용하시면 됩니다.
저는 topK를 5로 설정을 해두었고, 유사도가 높은 5개의 데이터를 조회하도록 하였습니다.
5개로 설정한 이유는 데이터 적합성을 확인하기 위해서입니다.
그리고 similarty Threadholds를 0.5 이상인것만 조회하도록 했는데, 이 thread holds를 지정해주지 않으면
연관없는 데이터를 조회해오는 환각증상을 일으킬수있기 때문에 0.5 이상만 조회하도록 설정해두었습니다.

만약에 이러한 조건을 아무것도 설정하지 않겠다고 하시면

5. API v3: LLM & 프롬프트 엔지니어링 - "AI의 뇌로 판단하기"
/v3은 시스템의 하이라이트인 Chat Client와 구조화된 출력입니다.

- Chat Client: Spring AI의 인터페이스를 통해 실제 LLM과 통신합니다.
- Prompt Engineering: 'bad-word-filter.st' 템플릿을 통해 AI에게 "너는 전문 검수관이야"라는 페르소나를 부여합니다.
명확한 가이드라인을 주어 답변의 정확도를 높이는 기술이죠.
- 구조화된 출력 (Structured Output): AI가 자유롭게 수다를 떨지 못하게 제어합니다.
BeanOutputConverter를 사용해 AI의 답변을 우리가 정의한 'LlmCheckResponse' 객체(JSON) 형태로 딱딱 맞춰서 받아냅니다.
프로그램이 즉시 처리할 수 있는 규격화된 데이터를 얻는 것이 핵심입니다.

6. API v4: 전처리(Preprocessing) - "꼼수 차단하기"
마지막 /v4는 실전 대응을 위한 전처리 단계입니다.

사용자들은 "바.보", "바   보", "B@bo"처럼 공백이나 특수문자를 섞어 필터를 피하려 합니다.
/v4에서는 BadWordPendingService를 통해 다음과 같은 3단계 정밀 전처리를 수행하여 이런 노이즈를 제거합니다.

1) 텍스트 정규화 및 클리닝 (Clean & Normalize)
- NFC 정규화: 한글 자음/모음이 분리된 경우를 대비해 표준 완성형 한글로 통일합니다.
- 노이즈 제거: 정규식을 이용해 특수문자, 공백, 이모지를 모두 제거하고 한글, 영문, 숫자만 남깁니다.
- 반복 문자 축소: "바보보보보"와 같이 필터링을 피하기 위해 반복된 글자를 "바보"로 축소하여 검사 효율을 높입니다.

2) 정규식(Regex) 기반 고속 필터링
- 특수문자나 숫자가 중간에 섞인 변칙적인 비속어 패턴(예: 시1발, ㅂㅅ 등)을 미리 컴파일된 거대 정규식으로 1차 차단합니다.
- 이는 DB 조회나 AI 호출 전 단계에서 가장 빠르고 효율적으로 명백한 비속어를 걸러내는 최전방 수문장 역할을 합니다.

3) 자모 분리 및 Fuzzy Matching (유사도 검사)
- "자모 분리(Decomposition)": 한글을 'ㅂ, ㅏ, ㅂ, ㅗ'와 같이 초성, 중성, 종성으로 분해합니다.
- "Jaro-Winkler 유사도": 분리된 자모를 바탕으로 DB에 등록된 비속어와 시각적/청각적 유사도를 계산합니다. (임계치 0.88 이상 차단)
- "슬라이딩 윈도우": 문장 속에 숨겨진 비속어를 찾기 위해 창문을 밀듯 한 글자씩 옆으로 이동하며 부분 일치 여부를 정밀하게 검사합니다.

이렇게 깨끗하게 정제되고 검증된 문장만이 RAG를 거쳐 LLM에게 전달됩니다.
"쓰레기를 넣으면 쓰레기가 나온다"는 격언처럼, 전처리는 AI 서비스의 신뢰도를 결정짓는 최전방 방어선입니다.

7. 클로징 (정리)
정리하겠습니다. 우리 프로젝트는 데이터를 비동기로 스마트하게 적재하고(Initializer), 의미를 숫자로 바꾸어(Embedding),
지식 저장소에서 검색하고(RAG), AI의 뇌를 빌려 정확히 판단(LLM & Prompt)한 뒤,
사용자의 꼼수까지 걸러내는(Preprocessing) 완벽한 AI 필터링 파이프라인을 구축한 것입니다.
